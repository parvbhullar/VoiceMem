CacheBlend × TurboQuant for Unpod
KV cache · Unpod context engine · research note

CacheBlend decides which KV to recompute. TurboQuant decides how many bits each KV value keeps.

They attack different bottlenecks, so they stack. CacheBlend cuts prefill compute when reused context is not the prefix. TurboQuant cuts the bytes every cached token costs in HBM, DRAM, NVMe and on the wire. Unpod's KV cartridges need both: CacheBlend to attach them anywhere in the prompt, TurboQuant to keep millions of them cheap and fast to move.

Fixes

Acts on

Reported

Architecture animation · 01

CacheBlend: fuse cartridges, repair cross-attention selectively

Each chunk's KV was computed alone, so it never attended to the chunks before it. Full reuse is fast but wrong; full recompute is right but slow. CacheBlend recomputes only the high-KV-deviation (HKVD) tokens, narrowing the set layer by layer, and hides that work behind loading the next layer from CPU or NVMe.

Per-request flow

    Architecture animation · 02

    TurboQuant: shrink every K/V vector without calibration

    Raw KV vectors have outlier channels, which is why ordinary low-bit quantization needs per-block scales and zero-points. A random rotation spreads the energy evenly, so one fixed grid works for every coordinate. A 1-bit Quantized Johnson–Lindenstrauss (QJL) sketch of the residual removes the bias in the query·key score that attention depends on.

      Why the two stack

      Cartridge size and load time

      CacheBlend can only hide loading if a layer of KV arrives before the previous layer finishes recomputing. Smaller cartridges let them live on slower, cheaper tiers without adding latency. Size per token is 2 × layers × kv_heads × head_dim × bits ÷ 8.

      Bandwidths are round planning figures, not measurements. TurboQuant rows ignore small per-vector norm overhead.

      Integration · context engine → inference engine

      One voice turn through the cartridge pipeline

      The context engine decides what the agent should know; the inference engine decides how cheaply the model can see it. The seam between them is the cartridge: compiled once by the Context Compiler, stored compressed, attached per request by the Context Runtime through the engine's KV connector, and repaired by CacheBlend.

      Request lifecycle

        Where each technique plugs into the engine

        vLLM + LMCache

        Implement the cartridge store as an LMCache backend and serve it through vLLM's KV Connector API. LMCache's blending mode already carries CacheBlend. Start with FP16 or FP8 cartridges; add TurboQuant first as an at-rest codec that the connector decodes on load, then as a custom attention backend once kernels exist.

        Fastest path to a working demo. Check the open non-prefix blending issues against the vLLM version you pin.

        TensorRT-LLM + Dynamo

        Dynamo's KV Block Manager (KVBM) already manages GPU, CPU, SSD and remote tiers, NIXL moves blocks between them, and LMCache integration is documented. Register cartridges as KVBM blocks and add TurboQuant as the tier codec. This is the natural place for the NVIDIA engineering asks on placement and runtime boundaries.

        Best path for multi-node serving and the million-user memory target.

        SGLang

        RadixAttention reuses exact prefixes and HiCache adds tiered storage, but neither blends non-prefix chunks. Use it for the stable system-prompt prefix and keep per-entity cartridges on vLLM or Dynamo until blending lands.

        Good for prefix-heavy flows; blending needs custom work.

        The cartridge contract

        A cartridge is only valid for the exact model, tokenizer and KV layout it was compiled against. The key has to say so, or the runtime will attach garbage.

        # cartridge id = hash of everything below
cartridge:
  entity_scope: [user:4411, org:88]      # A, A×B, B
  chunk_sha: 9f2c…                       # canonicalised text
  version: 17                            # bumps on memory write
  model: llama-3.2-3b-instruct@sha:1e0…
  tokenizer: sha:7ab…
  kv_layout: {layers: 28, kv_heads: 8, head_dim: 128}
  rope: {base: 500000, stored: pre_rotation}
  codec: tq3 | tq4 | fp8 | fp16
  tokens: 1840
  tenant_key: kms://unpod/tenant/88      # encrypt at rest

        Engineering notes

        • Positions. Compile each cartridge at offset 0 and store keys before RoPE, or store the offset and re-rotate on attach. CacheBlend relies on this to place chunks anywhere.
        • Blend in full precision. Decode TurboQuant cartridges to FP16/FP8 before HKVD selection, and write recomputed and new tokens in the engine's native paged format. Measure whether quantization noise changes which tokens get picked.
        • Prefetch during speech. On a voice call the Context Runtime knows the entities before the caller finishes. Start loading cartridges on the first ASR partial, so the endpointing pause covers most of the transfer.
        • Canonical order. Keep a stable order (system → org → user → A×B → turn) so the prefix portion hits exact prefix caching and CacheBlend only handles the rest.
        • Tenancy. Cartridges are derived from private memory. Scope them per tenant, encrypt at rest, and never share blocks across tenants even when chunk hashes match.

        Phase 1

        Blend

        vLLM + LMCache blending, FP16 cartridges in CPU DRAM. Context Compiler emits LMCache chunks keyed by the cartridge contract. Run arms A–C on one SLM.

        Phase 2

        Compress

        FP8, then TurboQuant as an at-rest codec on NVMe and remote tiers; decode in the connector. Run arms D–E and tune prefetch against ASR endpointing.

        Phase 3

        Scale

        Move to Dynamo KVBM + NIXL for multi-node tiering. With NVIDIA guidance, evaluate quantized attention kernels so cartridges stay compressed in HBM too.
